- **`capability.host-policy`:** Follow the active host's discovered project instructions and approval policy; treat AGENTS.md, CLAUDE.md, and MEMORY.md as project context rather than claims that the host loaded any particular capability.
- **`capability.tracker`:** Use linear_sync.py with the current session's authorized tracker access; if none is available, preserve the reviewed draft or outbox intent, report the pending synchronization to the owner, and never invent a receipt, ticket reference, or confirmation. (Elaboration: [tracker-sync.md](references/tracker-sync.md).)

- **`workflow.order`:** Run survey, interview, design, plan, ticket drafting and approval, dispatch, tracker drain, and evidence report in that order; each step's output is the next step's input.

- **`plan.decision-ledger`:** PLAN.md records each design decision with who made it (owner, committee or tiebreak) and lists the disagreements still open.
- **`plan.unit-contract`:** Each code unit's prompt carries a contract under the headings Claims, Supported envelope and accepted limits, Non-goals, Acceptance tests, and Requirement provenance; each requirement's provenance is an owner decision, an observed failure with its evidence, or the committee, and a requirement without provenance is removed. Each task records that unit's cardinalities, match counts and accepted grammar as acceptance cases. Committed fixtures are synthetic reconstructions, never redacted copies. - **`adoption.context`:** For a half-finished repository, read its README, CONTEXT.md, MEMORY.md, architecture decisions, recent history, and existing outputs before proposing remaining work. (Elaboration: [survey-interview.md](references/survey-interview.md).)
- **`repository.destination`:** For a discovered repository and remote: Adopt it. Do not ask. State the adopted remote and branch in one line before moving on. (Elaboration: [survey-interview.md](references/survey-interview.md).)
- **`repository.source-data`:** A repository is justified only when something must outlive the attempt directory as SOURCE; compute artifacts are data, reach shared paths only through promotion with a named approver, and nothing in this workflow may commit a swarm output to a repo. ## Run logging (W&B, required)

Every training run must log to Weights & Biases (default entity `goodarzilab`, one W&B project per project named in the plan). Log per-step train loss, learning rate, gradient norm, throughput, GPU memory, every evaluation point, and final checkpoint selection, plus full W&B config (recipe/config and its hash, Git SHAs, model/data pins and hashes, seed, fold, hardware/node, scheduler/job IDs, checkpoint paths/hashes, and resume/attempt lineage). Obtain the W&B key from a secret store or per-run credentials (never in files, bundles, logs, or the repo); without egress, log offline and sync afterwards. Logging must not alter numerics; a training unit without W&B logging is incomplete unless explicitly waived by the owner.

## Host capability boundary

The canonical declarations above are authoritative. Project files describe context; they do not prove that this host loaded a tool, connector, credential, account, or approval. Get from an empty directory or half-finished repo to dispatched, tracked, verifiable units without asking the human anything a machine could have looked up.

## Run from the loaded skills

Set `HANIG_PROJECT_DIR` to the directory containing the loaded `hanig-project/SKILL.md` (use colon-separated `HANIG_SKILL_DEP_ROOTS` only for deliberate mixed/link installs where `hanig-swarm` sits under a different parent):
```sh
export HANIG_PROJECT_DIR="/path/to/loaded/hanig-project"
P="$HANIG_PROJECT_DIR"
python3 "$P/scripts/skill_paths.py" self "$P" hanig-project >/dev/null || exit $?
S="$(python3 "$P/scripts/skill_paths.py" sibling "$P" hanig-project hanig-swarm)" || exit $?
```

Run steps 1–6 and the report in order; each step's output is the next step's input.

## 1. Survey. Never ask what you can read.
```sh
python3 "$P/scripts/survey.py" --repo . --out .swarm/survey.json
python3 "$HANIG_REVIEW_GATE_DIR/scripts/resolve_models.py" --project .
```
`resolve_models.py` moves each model seat to its newest probed point release for this project; report its `NEW_GENERATION` lines to the owner. Read the survey (host, Python, schedulers, partitions, accounts, memory flags, disk, repo history, protected docs, existing swarm state) and any adopted repo context before speaking; see [survey and interview evidence](references/survey-interview.md).

## 2. Grill. One question at a time, each with a recommended answer.

Invoke `grill-with-docs` if installed; otherwise follow its core rule directly:
> If a question can be answered by exploring the codebase, explore the codebase instead.

Follow the `repository.*`, `interview.*`, `cluster.*`, and `findings.interview` declarations above (do not restate the interview topic list here). Before ending the interview, run `python3 "$S/scripts/swarm.py" schema` so every required dispatch value is settled without placeholders ([survey and interview evidence](references/survey-interview.md)).

### Design with the planning committee

Put the survey output and interview answers (including fixed owner decisions) in `design-input.md`. Pass `--author PROVIDER/MODEL` for the proposal's author(s) (`NAME` is the session):
```sh
python3 "$HANIG_REVIEW_GATE_DIR/scripts/committee.py" open NAME --profile planning --problem-file design-input.md --author PROVIDER/MODEL
python3 "$HANIG_REVIEW_GATE_DIR/scripts/committee.py" ask NAME --with-peers --prompt "Cross-critique the other member's design against the survey and owner decisions; identify disagreements and untestable requirements." --author PROVIDER/MODEL
python3 "$HANIG_REVIEW_GATE_DIR/scripts/committee.py" synthesize NAME --author PROVIDER/MODEL
```
Send divergence to `committee.py tiebreak NAME` or the owner. Synthesis requires the current owner mandate; an absent mandate or unavailable/author-conflicted committee goes to the owner. Record decisions, makers, and open disagreements in `PLAN.md`, and put each code unit's five-heading contract in its prompt ([unit contract examples](references/unit-contract.md)).

After writing `PLAN.md` and `plan.json`, run one advisory plan review replacing `PROVIDER/MEMBER_1` and `PROVIDER/MEMBER_2` with the session's actual authors (plus tiebreak if it decided), and pass `--file .swarm/PLAN.md` instead of `--file PLAN.md` when protected documents redirected the plan; record unavailable reviews as unavailable without dropping `--author`:
```sh
python3 "$HANIG_REVIEW_GATE_DIR/scripts/review.py" --kind plan --file PLAN.md --file plan.json --author PROVIDER/MEMBER_1 --author PROVIDER/MEMBER_2
```

## 3. Plan. Units are defined by their OUTPUTS, not their commands.

Size units by retry exposure (`hanig-swarm/SKILL.md` `retry.*` declarations) and below 100,000 review-input characters per code PR. Preflight size and run implementation reviews against the complete committed delta (`--target REF` if not `origin/main`; keep `--plan-name`/`--unit` stable across fixes; pass behavioral claims and `--author PROVIDER/MODEL`):
```sh
python3 "$HANIG_REVIEW_GATE_DIR/scripts/review.py" --size --range BASE..HEAD
```
```sh
python3 "$HANIG_REVIEW_GATE_DIR/scripts/review.py" --kind implementation \
  --range BASE..HEAD --round 1 --plan-name NAME --unit UNIT \
  --claim "This change cannot make an honest run fail."
```

### The unit contract, by kind

| | `slurm` | `pipeline` | `code` |
|---|---|---|---|
| `command` is | the work itself | the engine invocation | **not used** |
| the prompt goes in | n/a | n/a | `prompt`, and only there |
| submitted by | the coordinator, so **never** `sbatch`/`srun` here | the coordinator | `paseo run` |
| configured by | `sbatch` flags | `command` | fields: `provider`, `mode`, `model`, `thinking`, `env` |
| `outputs` are | relative to the run-dir | relative to the run-dir | relative to the run-dir |
| judged by | Slurm accounting + declared outputs | launcher exit + declared outputs | agent lifecycle + outputs + a produced commit |
| closed by | a predicate receipt | a predicate receipt | a **merged PR** |
| also needs | surveyed memory/account flags | fresh work and publish dirs | `repo`, `target_branch`, explicit `mode` |

Read [unit contract details](references/unit-contract.md) for failure examples and `python3 "$S/scripts/swarm.py" schema` for the field reference, write `plan.json` and `PLAN.md` (or `.swarm/PLAN.md` when `protected_docs` requires redirect), and always validate before ticketing or dispatch:
```sh
python3 "$S/scripts/swarm.py" validate plan.json
```

## 4. Tickets. Draft everything, create on ONE approval.
```sh
python3 "$P/scripts/tickets.py" draft plan.json --brief brief.json --repository OWNER/REPO
```
Team defaults to `Arc` (`--team` overrides; `charge_to` is a Slurm account, not a tracker team). **THE DEFAULT IS TO STOP HERE.** While `approval.state` is `"required"`, create nothing: show the human the project, every issue title in full, and the count, then record named approval and file through the authorized operator (`--autopilot` only on the literal phrase `swarm autopilot`):
```sh
python3 "$P/scripts/tickets.py" approve tickets.json --approver <name>
python3 "$P/scripts/linear_sync.py" file --draft tickets.json [--preview]
python3 "$P/scripts/linear_sync.py" replay OPERATION_ID --draft tickets.json
```
The binding lives at `.hanig/linear-binding.json` beside the draft. For an independently supplied edge read-back (`{"schema_version": 1, "read_at": "<ISO 8601>", "source": "...", "edges": {"<issue>": ["<blocker>", ...]}}`, empty list required for observed absence; without it `remove_blocked_by` stays `null`) and orphan/sync checks:
```sh
python3 "$P/scripts/tickets.py" draft plan.json --tracker-edges edges.json
python3 "$P/scripts/tickets.py" reconcile plan.json --tracker-issues issues.json --json
python3 "$P/scripts/tickets.py" check plan.json tickets.json
```
See `tracker.*` declarations above and [tracker synchronization details](references/tracker-sync.md).

## 5. Dispatch.
```sh
python3 "$S/scripts/swarm.py" run plan.json --dry-run   # shape first
python3 "$S/scripts/swarm.py" run plan.json
```
Schedule `advance` with cron or a Paseo schedule; the coordinator's OS lock serializes overlapping runs.

## 6. Drain. Issue state follows unit state, never the reverse.
```sh
python3 "$S/scripts/swarm.py" outbox --json
python3 "$HANIG_PROJECT_DIR/scripts/linear_sync.py" drain \
  --binding .hanig/linear-binding.json --state-dir "$STATE"
python3 "$HANIG_PROJECT_DIR/scripts/linear_sync.py" audit \
  --binding .hanig/linear-binding.json --out "$AUDIT"
```
Use `--draft tickets.json` for a named plan with filed unit mappings; repeat `--state-dir` across waves; `--dry-run` previews without mutating Linear or writing receipts. `start`, `close`, and `reopen` target started, completed, and unstarted; `note`, `block`, and `open_pr` post comments only (drain does not create PRs).

- **An issue closed without its authorised evidence is an integrity violation.** Say so loudly and reopen it. Never mark the intent applied because the issue "looks done": the drain must refuse a close without its authorised evidence, and the operator must report and correct the violation.

Drain sorts pending comments by instant, legacy before sequenced, sequence, and key, reconciling each touched issue once (receipting the latest state intent after comment + state read-back, comment-only intents after comment read-back). One host serializes drainers per project; competing hosts and lagging listings require a successful covering drain after writes stop and comments become visible, while comment edits/deletions and uncovered legacy history remain declared limits ([tracker synchronization details](references/tracker-sync.md)).

## Last step, every run: the report

A run is not finished until `report.py` runs (not when the last unit reaches DONE or issues close); publish the fragment as an artifact and give the human the link:
```sh
python3 "$P/scripts/report.py" . --out report.html            # standalone
python3 "$P/scripts/report.py" . --fragment --out frag.html   # to publish
python3 "$P/scripts/report.py" . --json                       # for a machine
```
When the interview establishes publishable findings, declare and promote `findings.json` (`{"outputs": ["findings.json"], "promote_to": "/abs/path/to/the/project"}`) with shape `{"findings": [{"title": "one actionable sentence", "detail": "measured bounds and what they do NOT prove"}]}`; see [reporting evidence details](references/reporting-evidence.md).

## Adopting a half-finished repo

Survey, read docs and history, then bring the human a draft of remaining units with outputs to grill against rather than starting from a blank page. Follow `adoption.*` and `plan.docs-protection` above.

## What this never does

Never create/modify tracker items without explicit approval, close an issue on an agent's say-so, write to shared paths outside `swarm.py promote --approver`, ask what the survey answered, or report a run finished from recollection instead of receipts.
