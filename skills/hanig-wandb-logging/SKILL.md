# hanig-wandb-logging

## Host capability boundary

Use the host's available shell, filesystem, Python and authorized W&B access.
This skill installs no W&B package, connector, credentials or service. Missing
access is a blocked logging check, not evidence about training. The caller's
training project imports W&B and passes the module explicitly; both shipped
scripts import only the standard library. Measured with wandb 0.31.0; other
versions are best effort.

Set `HANIG_WANDB_LOGGING_DIR` to the directory containing this loaded SKILL.md.
Copy [wbkit](scripts/wbkit.py) from that directory into the training project.
For audits, add its `scripts` directory to the caller's `sys.path`; project
input and output paths remain relative to the project directory.

## Boundary

This skill makes runs readable. It never decides whether a run succeeded or
converged. Verdicts come from hanig-verified-workflow contracts and
hanig-swarm/converge.py predicates. The `Expect:` line quotes the predicate
declared before the run. A checkpoint chosen after seeing results is labeled
post hoc in the artifact card's caveats. `finish` records a caller-supplied
verdict; it computes no scientific verdict. The training logging policy lives
in hanig-project and hanig-swarm; this skill explains how to apply it.

A W&B project is only as useful as what a stranger (or you, in six months) can
recover from it without opening the code. Default W&B gives random run names,
empty notes, flat configs, un-namespaced metrics and artifacts with no
description. This skill makes the write side carry its own explanation.

[scripts/wbkit.py](scripts/wbkit.py) implements every convention below as a single vendorable
file. Prefer copying it into the user's repo over re-deriving the logic inline.

## Workflow

### 1. Survey before editing

Read the training entry point and answer these from the code, not by asking:

- Framework: raw PyTorch, Lightning, HF Trainer, Accelerate, JAX. See
  [references/frameworks.md](references/frameworks.md) for how each one creates its run.
- Config system (Hydra, OmegaConf, argparse, dataclass, YAML) and where the
  seed lives.
- Data inputs: paths, URIs, sizes, whether they already exist as artifacts.
- Checkpointing: cadence, where files go, how "best" is decided.
- Distribution and scheduler: DDP/FSDP ranks, Slurm requeue or preemption.
- Existing W&B calls: keep anything that already follows the conventions.

### 2. Write a logging plan and show it

Before touching code, present a short plan with the concrete strings filled in:

```
entity / project   arc-ml / state3-pretrain
group              20261109-mask-ratio-ablation
job_type           train
run name           state3-tahoe100m-mask0.3-s0      (deltas vs base config)
tags               ablation, data:tahoe100m
notes              H: masking 30% of genes beats 15% on held-out cell lines.
                   Expect: val/pearson_delta +0.02 or more.
step axis          trainer/step (optimizer steps)
metrics            train/loss, val/loss[min], val/pearson_delta[max], opt/lr,
                   opt/grad_norm, perf/samples_per_s, perf/gpu_mem_gb
inputs             arc-ml/state3-pretrain/tahoe100m-hvg2k:v3
outputs            ckpt-<run_id> (model, aliases step-N, best), every 5k steps
                   preds-<run_id>-replogle-k562 (predictions), at end
```

Project, entity and group naming are the user's decisions the first time;
infer them from existing projects if any (call `audit_project.audit(wandb.Api(), "entity/project")` or
look at `wandb.Api().projects(entity)`), otherwise propose and confirm. After
that, apply the plan without re-asking.

### 3. Implement

Vendor [scripts/wbkit.py](scripts/wbkit.py), then wire it in. Minimal raw-PyTorch shape:

```python
import wandb  # installed by the training project
import wbkit

run = wbkit.start_run(wandb, 
    project="state3-pretrain", family="state3", job_type="train",
    model="state3", data="tahoe100m",
    hypothesis="Masking 30% of genes beats 15% on held-out cell lines.",
    expect="val/pearson_delta +0.02 or more",
    config={"arch": arch_cfg, "train": train_cfg, "data": data_cfg},
    base_config=base_cfg,                 # the group's reference config
    group="20261109-mask-ratio-ablation",
    tags=["ablation", "data:tahoe100m"],
    summaries={"val/loss": "min", "val/pearson_delta": "max"},
    output_dir=out_dir,                   # stable id across Slurm requeues
)
ds = wbkit.use_input(run, "arc-ml/state3-pretrain/tahoe100m-hvg2k:v3")
...
wbkit.log_step(run, step, {"train/loss": loss, "opt/lr": lr, "perf/samples_per_s": sps})
...
wbkit.log_model(wandb, run, ckpt_path, step=step, metrics={"val/loss": vl}, is_best=vl < best)
...
wbkit.finish(run, outcome="val/pearson_delta +0.031 at 40k steps; 3 seeds agree.",
             verdict="supported")
```

`start_run` returns a disabled run on non-zero ranks, so metric call sites need no
rank guards. `finish` writes the outcome into notes, sets `summary.verdict`,
prints lint issues, then closes the run.

### 4. Verify with a smoke run

Run a few steps with `WANDB_MODE=offline` (or the project's debug flag and
`job_type="debug"`) before the real launch. Confirm: no lint lines from
`finish`; the run name reads as intended; config holds `arch`, `train`, `data`
and `provenance.git_commit`; every logged key has a namespace; each artifact
description renders as a card. Keep `output_dir` outside the repo or
gitignored, or every run is flagged `dirty-tree`. Report what the smoke run
showed, not what the code is expected to do.

### 5. Clean up an existing project

From a caller that imports W&B, the read-only audit is:

```python
import wandb, audit_project
report = audit_project.audit(wandb.Api(timeout=120), "entity/project", 200)
```

It is read-only. It groups
problems by rule code (`name.random`, `notes.empty`, `artifact.thin-card`, ...).
Propose fixes from its output. Renaming runs, rewriting notes or tags, and
editing artifact descriptions through `wandb.Api()` changes shared state:
show the exact before/after list and get confirmation first. Never delete runs
or artifact versions as cleanup; tag them `broken` instead.

## The conventions, briefly

Full rules and examples: [references/naming.md](references/naming.md) (projects, groups, runs, tags,
notes, config, metric keys) and [references/artifacts.md](references/artifacts.md) (types, names, the
description card, metadata, references vs uploads, aliases, lineage).

- **Project** is a comparison boundary: runs that share a metric schema and
  should sit in one table. One per model family or research program, kebab-case.
  Not per person, per date or per sweep.
- **Group** is one question: an ablation, a seed set, a sweep.
  `YYYYMMDD-<slug>` so groups sort by time.
- **job_type** comes from a fixed vocabulary: `preprocess`, `train`,
  `finetune`, `eval`, `predict`, `sweep-trial`, `debug`.
- **Run name** is `<model>-<data>-<deltas>-s<seed>`, where deltas are only the
  hyperparameters that differ from the group's base config.
- **Notes** open with `H:` (why this run exists) and `Expect:`, and close with
  `Outcome (<verdict>):`. This is the single most informative field.
- **Config** is nested `family / arch / train / data / provenance`. This maps
  directly onto the Arc Bench Training contract (`architecture.config`,
  `training.config` with seed, `training_data`, `run.commit`), so a later export
  needs no guessing.
- **Metrics** are `<namespace>/<name>` on the one step axis `trainer/step`;
  units go in a suffix when not obvious (`_s`, `_gb`). Declare `min`/`max`
  summaries so the runs table shows the best value, not the last.
- **Artifacts** have stable logical names (no versions, dates or "final"),
  one of five types, a description card, flat searchable metadata, and inputs
  consumed through `use_artifact` with a pinned `:vN`.

## Failure modes to catch in review

- `wandb.init()` on every rank: N duplicate runs, or one run with interleaved
  garbage.
- `step=` passed to `run.log` that goes backward after a resume: W&B drops
  those points silently. Use the `trainer/step` metric instead of `step=`.
- Logging val metrics without `define_metric`: they plot against W&B's
  internal step and misalign with train curves.
- `log_model=True` in Lightning or `WANDB_LOG_MODEL` in HF uploading every
  checkpoint with an empty description. Turn them off and log via `wbkit`.
- Large cluster datasets uploaded as bytes. Use references (`wbkit` does this
  above 2 GiB) and state the host or mount in the card's caveats.
- Secrets in config or command line. `wbkit` redacts keys and argv that look
  like tokens, passwords or API keys; check custom fields anyway.
- `latest` treated as "best". `latest` only means newest.

## Querying afterwards

For reading runs back (best run, curve comparisons, sweep summaries), the
official `wandb/skills` `wandb-primary` skill is better suited. The conventions
here make its queries easy: filter by `group`, `job_type`, `tags`,
`summary_metrics.verdict` and `config.train.*`.
